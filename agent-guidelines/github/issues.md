# Issues

Directives for creating, triaging, and closing GitHub issues.

## Creation

- Title: clear and specific — state the problem or feature, not a vague summary.
- Body must contain: explicit context, a clear problem statement, clearly defined action items required to fix it, and acceptance criteria for when it's considered fixed (or a testing plan for the fix).
- Break large issues into smaller, manageable sub-issues, creating a hierarchical parent-child relationship between issues where the scope warrants it.

## Quality Bar

- Bug reports require: reproduction steps, expected behavior, actual behavior.
- Feature requests require: a clear, bounded scope — what is and is not included.
- Search existing issues before creating a new one to avoid duplicates.

## Triage

- Apply appropriate labels (type, priority, area) using the repository's existing label set.
- Link related issues and PRs explicitly rather than describing the relationship in prose only.

## Closure

- Close an issue only when its stated acceptance criteria are met.
- Reference the PR or commit that resolved it when closing.
- Set a state reason (e.g., completed, not planned) when the tooling supports it.
